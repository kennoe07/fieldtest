# Durable reward transaction intents

Apply **007_reward_intents.sql** once after migration 006, then deploy this commit. No new environment variables are required. This is private server infrastructure: no public endpoint, wallet prompt, transaction submission, scheduler or funded UI flow is activated.

## Reuse and state

The checked prepare RPC derives create/enroll/submit/approve/refund arguments from the saved plan, verified wallet, accepted terms and feedback. The future endpoint must obtain the actor from a verified session. A request UUID identifies a retry; identical live actions also reuse their existing intent across different request keys. Different actions cannot share an actor/request key. A pending action blocks conflicting versions for the same actor/plan/action/tester.

For feedback submission the RPC reuses the saved commitment matching the exact current snapshot. Separate server calls may generate different candidate salts; under the plan lock only the selected saved commitment is used. Creating a commitment and its intent happens in one database transaction. A conflict rolls back the candidate commitment too. `prepareRewardIntent` returns the persisted payload, which is authoritative; callers must not substitute their locally generated candidate hash.

States:

- **Prepared**: no transaction attached. May be cancelled. Expires after at most 15 minutes, capped by the action deadline. A new request can replace an expired/cancelled unsigned intent. An old request key returns its terminal record while the action remains preparable; load the intent directly after plan/review state changes.
- **AwaitingWallet**: exact unsigned transaction bytes and digest have been bound. They cannot be replaced. Wall-clock expiry and wallet rejection do not release this action: the bytes may have been signed or executed elsewhere. Resume/reconcile the same transaction.
- **Submitted**: a matching digest was reported, but payment is not yet established. Timeouts keep this state pending.
- **Failed**: a trusted reconciler checked the bound digest on the pinned network and found a checkpointed execution failure. A fresh request key may then prepare another attempt; the old record remains immutable in its transaction identity.
- **Confirmed**: create/approve/refund have a matching verified ledger receipt and saved proof. Enrollment/submission confirmation remains unsupported until their chain verifiers are implemented. Confirmed intents cannot be marked failed or replaced.

There is no automatic expiry for armed transactions. If a transaction cannot be found, the RPC is unavailable, or a wallet prompt is rejected, reconciliation leaves the action pending. A future verifier for provable on-chain transaction expiration will be needed to release such intents safely; do not use elapsed time alone.

## Trust and activation boundary

Only the service role can call the intent RPCs. Browser roles cannot read stored bytes or modify intent rows. Even the service role has select-only direct table access; writes use checked functions. Database administrators remain trusted.

The bind RPC stores bytes/digest but does not parse transaction bytes or independently calculate a Sui digest. Before invoking it, a future trusted builder must assemble from the persisted payload, resolve gas/coin inputs, enforce sender/package/asset/action arguments, simulate, compute/validate the digest, and bind the exact unsigned bytes before displaying a wallet prompt. Never pass browser-generated bytes to that RPC. Signatures and private keys are not stored. No binding/execution endpoint is implemented in this slice.

Failure settlement is service-only and must go through a trusted chain check such as `reconcileFailedRewardIntent`; direct SQL cannot authenticate blockchain responses. Successful financial settlement depends on the existing verified event/proof ledger. Database review approval is required to prepare a payout, but is not itself payment. This work does not remove the need for on-chain idempotence or replace the contract's one-payout protection.

## Tests and remaining work

`npm run test:reward-intents` checks helper guards, network-bound checkpointed failure reconciliation, actual PostgreSQL migration behavior, commitment reuse, cancellation/expiry, immutable binding, conflicting pending actions, stale retries, private access and financial proof requirements. Fixtures use synthetic ledger receipts and unsigned bytes; no real chain call or wallet signature occurs.

Next: explicit testnet policy/asset support, semantic transaction construction and simulation, authenticated intent endpoints/UI recovery, enrollment/submission event verification, and end-to-end testnet validation. Slush review/wallet ownership verification, API billing for AI findings, and the deferred domain/custom email sender remain separate launch items. Live payments remain inactive.
